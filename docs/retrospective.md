# Project Retrospective

**Project:** Isaac Ihebom | Personal Profile (CMPA 3301)
**Author:** Isaac Ihebom

## Introduction

This retrospective looks back at how I planned and built my personal profile website. I set out to make a clean, simple page that introduces who I am, what I'm studying, and where I want my career to go, while practicing HTML, CSS, and Markdown. Looking back means I can see not only what I made but how I worked, which is useful because I want to carry these habits into a cybersecurity career.

## What went well

**A clear scope kept the project manageable.** Writing a scope first gave me a target: one simple page, no accounts, animations, or interactive features. The finished site matches what the scope promised: my name, major, career goals, hobbies, and a GitHub link.

**The page structure is clean and easy to read.** The HTML uses meaningful sections like a header, a main area with "About me" and "My hobbies," and a footer, which makes the content easy to follow and to update. The "At a glance" box gives a the user the key summary about me (major, graduation, field) in a few seconds, which matches the scope's goal that someone can get to know me quickly.

**The writing sounds like me.** One of my goals was to sound personal and natural instead of formal or performative. The About section sounds like the way I would talk about my goals if I was in person, and it including why I've been fascinated by computers since I was a kid.

**I learned by building and doing research.** Working in HTML, CSS, and Markdown together, and keeping everything in one GitHub repository, taught me how the pieces connect: the README is the entry, the docs explain the thinking, and the website is the result.

## What went wrong

**My early writing had typos and rough phrasing.** The first scope draft had spelling mistakes and some awkward wording. That's a small thing, but it matters on a page whose purpose is to make a good impression. It happened because I wrote quickly and didn't proofread until late.

**The documents got disorganzed.** The scope said the project would have two files scope.md and index.html, and a style.css, but my project grew to have a README.md, plan.md, and retrospective.md.  I didn't go back and update the scope to match, which means the files described an earlier version of the project than the one I built.

**Organization of the repository was an afterthought.** I built the page first and thought about the required structure (README file) later. That meant me moving files around at the end, which added stress that a plan would have avoided.

**Some content is thin.** The hobbies section is just three items with no detail, and the page tells a user about my goals but doesn't yet show any project work beyond linking to GitHub. My scope said the page should show my growth over the semester, but the page only hints at that.

**Time management was uneven.** Like a lot of students taking classes like this, my work bunched up near the due date instead of following the schedule in my plan. The critical path items got done, but I had less time for review than I wanted.

## What I would do differently

1. **Plan the repository structure on day one.** I would create the `docs/` folder and the README draft first, so nothing needs to be reorganized at the end.
2. **Proofread.** Reading everything out loud before committing would catch typos and awkward sentences.
3. **Update the scope whenever the project changes.** When I add more files and changes, I should have revisit the scope right then, so the documents always match the work.
4. **Add evidence of growth.** I would put a short "what I've learned" or "projects" section on the page, or link to specific GitHub repositories, so the site shows growth and not just goals.
5. **Get feedback sooner.** Peer feedback made the scope better. Asking for it on the page itself, earlier in the process, would have improved that too.

## Lessons for the future

- A short, honest scope is more valuable than a long one.
- Documentation is part of the project, not something extra after it. Keeping it current takes minutes, and rewriting it later takes much longer.
- Frequent commits and regular checking of the live site prevents last-minute surprises.
- These habits (planning, managing risk, and reviewing my own work) are the same ones I'll need in cybersecurity, where careful process matters as much as technical skill.

## Conclusion

Overall, the project achieved what I set out to do: a clean, readable personal page that reflects my goals and interests. The biggest lessons were to plan the structure early, proofread carefully, and keep the scope and plan in sync with the real work. I'm stoked of how the site turned out, and I now have a base to build on as my skills grow.
